# 考核标准与答辩形式

## 1. 评分构成（满分 100）

| 维度 | 权重 | 考察内容 |
|---|---|---|
| **知识掌握（答辩）** | 35 | 算法原理（推导、假设、适用条件）；系统机制（[core-knowledge.md](core-knowledge.md) + 项目专项）；能否解释自己的设计决策和实验现象 |
| **实现与正确性** | 20 | HF 参考实现 + 引擎内实现的完成度；正确性测试；代码可读性与可复现性 |
| **实验与鸿沟分析** | 30 | 质量 + 效率双重评测是否完整可信；是否按 [benchmarking.md](benchmarking.md) 报告了多 batch size 下的真实加速；**能否讲清楚理论加速与真实加速之间的差距从何而来** |
| **文档与汇报** | 15 | 报告结构清晰、图表规范、DEVLOG 完整、汇报表达清楚 |

### 一票否决项

- 答辩时**无法解释项目的核心算法或核心落地机制**；
- 只报告 batch=1、关闭 CUDA Graph 等"有利条件"下的加速，并以此作为主要结论；
- 触碰 [guidelines.md](guidelines.md) 中的任意红线。

### 加分项

- **系统感知的算法改进**：基于鸿沟分析提出的算法改进，并在真实引擎中验证有效。这是我们最看重的研究能力；
- 向 vLLM / SGLang 等上游提交 PR 并被合入，或获得实质性 review；
- 发现有研究价值的现象，并形成可以发展为论文的 idea。

## 2. 答辩形式

**总时长约 40 分钟**：

1. **汇报（20 分钟）**
   - 算法背景：方法原理、论文声称的收益（4 分钟）
   - 落地方案：接入点选择、遇到的系统约束、关键设计（6 分钟）
   - 实验：质量 + 效率、多 batch size、鸿沟分析（7 分钟）
   - 改进与总结：系统感知的改进（如有）、局限性、收获（3 分钟）
2. **Live Demo（5 分钟）**：现场在引擎上运行，展示加速效果（以及在什么条件下不加速）
3. **问答（15 分钟）**
   - **算法追问**："这个方法为什么能保持精度？它的核心假设是什么？在什么输入上会失效？"
   - **系统追问**："你的实现和 CUDA Graph / prefix caching 是怎么共存的？"
   - **估算题**：现场估算与项目相关的量，例如某 batch size 下 decode 的算术强度
   - **反事实题**："换成 H100 / 4090、换成 70B 模型、换成长上下文，结论还成立吗？"
   - **代码走读**：随机指定一段核心代码请你讲解
   - **Agent 相关**：在这个项目里，Agent 最大的帮助和最大的坑分别是什么？

## 3. 中期检查（M2）

形成性评价，不计入总分，但需要满足以下条件才能进入后半程：

- HF 参考实现完成，精度与论文基本对齐（或能解释差异）；
- 引擎内实现的主路径跑通，有正确性测试；
- 至少有一组 batch=1 与一组较大 batch 的真实加速数据；
- DEVLOG 持续更新。

## 4. 提交物清单

- [ ] 代码仓库：HF 参考实现 + 引擎内实现（fork 或插件）+ README
- [ ] `experiments/` 目录：所有实验的一键复现脚本 + 原始数据
- [ ] `DEVLOG.md`
- [ ] 结题报告（[模板](../templates/final-report.md)）
- [ ] 答辩 Slides
- [ ] （可选）上游 PR 链接
