# AI Agent 使用规范

本项目集**鼓励并期望**你用 AI Agent（Claude Code、Codex、Cursor、Gemini CLI 等）完成大部分编码工作。下面这份规范说明三件事：怎么用好 Agent，什么是你必须亲自掌握的，以及哪些是红线。

---

## 1. 基本立场

- **Agent 是你的工程团队，你是 Tech Lead。** 你负责理解问题、拆解任务、设计方案、审查代码、设计实验、解读结果。Agent 负责把这些落成代码。
- **"能解释的才是你的。"** 答辩时，你提交的代码和数据要能逐项讲清楚：
  - 这个模块为什么这样设计？还考虑过哪些方案？
  - 这个数字是怎么测出来的？为什么可信？
  - 改动的关键路径在上游代码哪里，数据怎么流过去？
- 不要求你记住 API 细节或手写 CUDA，但**机制层面的理解不能外包**。

## 2. 推荐工作流

### 2.1 读代码阶段：让 Agent 帮你建地图，但你要自己验证

vLLM、SGLang 这类代码库有几十万行，Agent 很适合帮你快速定位。建议这样做：

1. 让 Agent 梳理目标模块的调用链，例如"一个请求从 API Server 进来，到 Scheduler 分配 KV block，再到 ModelRunner 执行"，并生成一份带文件路径和行号的笔记；
2. **你自己**打开关键函数逐个确认，再**手画一张架构图/时序图**，这张图会用于答辩；
3. 用调试器或打日志实际跑一个请求，确认你的理解和真实执行一致。

> Agent 对大型代码库的描述经常"大体对、细节错"，特别是版本相关的细节。只看它的总结不读源码，很容易在答辩中被问住。

### 2.2 算法复现阶段：HF 参考实现是"金标准"，必须由你把关

本项目集中，HF 参考实现是后续所有引擎实现的正确性基准，它错了，后面全错。因此：

- 对照论文公式和官方代码**逐行审查** Agent 写的算法实现，特别是 mask、索引、归一化、采样这些细节；
- 先在论文报告的设置下复现精度，**对不上就先查清原因**，不要急着进入引擎落地；
- 算法的推导（例如投机解码为什么无损、量化误差从哪里来）要自己能在白板上讲清楚，不能只依赖 Agent 的解释。

### 2.3 设计阶段：先写设计文档，再写代码

- 动手前写一页设计文档：要改哪些地方、新增哪些组件、接口长什么样、怎么测；
- 可以和 Agent 讨论方案，但**最终方案要由你拍板**，并在 DEVLOG 中写下理由。

### 2.4 实现阶段：测试先行，小步提交

- 先让 Agent 写测试（正确性测试优先，例如"开启新功能后输出与 baseline 逐 token 一致"），再写实现；
- 每个功能点单独提交，commit message 写清楚改了什么；
- **每次 Agent 改完都要跑测试**。对推理引擎来说，"能跑"和"结果对"是两回事，静默的精度错误最难查。

### 2.5 实验阶段：实验设计是你的工作

- Agent 可以写 benchmark 脚本、画图脚本；
- 但**实验设计**（测什么、对比谁、控制什么变量、负载怎么选）必须由你决定，并能说明理由；
- 任何"好得不正常"的结果，都要先怀疑是 bug（缓存没清、warmup 没做、测错了对象），而不是先写进报告。

## 3. 开发日志（DEVLOG）要求

每个项目维护一份 `DEVLOG.md`（[模板](../templates/devlog.md)），至少每周更新一次，内容包括：

- **关键决策**：做了什么选择、为什么；
- **Agent 犯过的错**：Agent 给出的错误方案或 bug，你是怎么发现、怎么纠正的。**这一项很重要**，它最能体现你的判断力，答辩时会重点看；
- **实验记录**：每次实验的配置、结果、异常与解释；
- **卡住的地方**：遇到了什么问题，最后怎么解决（或没解决）。

## 4. 有效使用 Agent 的技巧

- **给足上下文**：告诉 Agent 锁定的上游版本、相关文件路径、你的设计文档，以及要遵守的约束（如"不改动 Scheduler 的公共接口"）；
- **限定改动范围**：明确"只修改 X 文件"，避免 Agent 在大型代码库里四处改；
- **要求它先解释再修改**："先告诉我你打算怎么改、为什么，确认后再动手"；
- **让它写可验证的产出**：测试、断言、日志、最小复现脚本；
- **善用 Agent 做重复劳动**：参数扫描脚本、绘图、日志解析、格式转换；
- **警惕幻觉 API**：Agent 可能编造不存在的参数或函数，尤其是对快速迭代的项目。以源码为准。

## 5. 红线（触碰即判定不通过）

1. **伪造或篡改实验数据**，包括把 Agent 编造的、未实际运行得到的数字写进报告；
2. **隐瞒关键代码来源**，例如直接搬运某个开源 PR 却声称是自己实现的（借鉴可以，**必须注明**）；
3. **答辩时无法解释自己项目的核心机制**（见 [evaluation.md](evaluation.md) 的一票否决项）。

## 6. 鼓励的行为

- 向上游社区提 Issue/PR。如果你的实现足够好，努力合入 vLLM/SGLang，这本身就是很好的成果；
- 公开分享你的 Agent 使用经验，例如好用的 Prompt 和工作流，可以更新到本仓库；
- 把 Agent 没能解决、需要你自己深入调试才解决的问题，整理成技术笔记。
