# P02 · 大 Batch 下的投机解码：让加速真实存在

> **难度** ★★★★ ｜ **算法 : 系统** 6 : 4 ｜ **建议人数** 1–2 ｜ **最低硬件** 1×80GB ｜ **基座** vLLM 或 SGLang

## 1. 背景

投机解码论文几乎都报告 batch=1 下的加速。但真实服务中 batch 通常很大，而投机解码的收益前提是 **GPU 有空闲算力**：

- batch 小时，decode 是 memory-bound，多验证几个 token 几乎免费；
- batch 大时，系统接近 compute-bound，验证被拒绝的 token 是纯浪费。

已有的测量很直接：
- *Speculative Decoding: Performance or Illusion?*（MLSys 2026）：vLLM 上，目标模型验证占主导开销，真实加速远低于理论上界；接受长度在不同 token 位置、不同请求、不同数据集之间差异很大；
- Meta 的生产测量显示，batch 从 2 增加到 48 时，vLLM 中 EAGLE 的加速从 1.3× 降到 0.7×，**变成了减速**；
- MagicDec 指出，在长上下文、大 batch 下瓶颈转向 KV Cache 读取，用稀疏 KV 的草稿器反而可以在大 batch 下获得加速。

这意味着：**投机解码在真实服务中需要"算法级"的自适应决策**：何时投机、对谁投机、投机多长。这本质上是一个在线决策 / 优化问题，非常适合算法背景的同学。

## 2. 项目目标

1. 在真实引擎中系统刻画投机解码收益随 batch size、上下文长度、领域、投机长度的变化，建立**可预测的代价模型**；
2. 设计并实现**批感知（batch-aware）的自适应投机策略**，至少包括：
   - **全局层面**：根据当前 batch 负载选择投机长度，必要时关闭投机；
   - **请求层面**：根据每个请求的历史接受率 / 置信度，为不同请求分配不同的投机长度；
3. 在全部负载区间内，做到**不劣于"不投机"和"最佳静态配置"**，并在中等 batch 下显著优于二者。

## 3. 论文 → 引擎的鸿沟

| 问题 | 说明 |
|---|---|
| 代价模型不准 | 论文的加速比公式假设验证代价恒定，真实引擎中验证代价随 batch、序列长度、token 数非线性变化 |
| 接受率是非平稳的 | 随领域、位置、请求变化，需要在线估计 |
| 每请求不同的投机长度 | 导致 batch 内不规则，与 CUDA Graph、kernel 效率冲突 |
| 决策本身有开销 | 每步做决策的 CPU 开销在小模型上不可忽略 |

## 4. 任务分解

### 4.1 阶段一：刻画与建模（必做）
- 使用 EAGLE-3（或 MTP）作为基础方法，在引擎中扫描：并发度 × 投机长度 × 领域 × 上下文长度；
- 测量单步验证耗时与 (batch size, 每请求验证 token 数, KV 长度) 的关系，拟合**代价模型**；
- 测量接受率的分布与可预测性：草稿器置信度、历史接受率、token 位置对接受与否的预测能力。

### 4.2 阶段二：自适应策略（必做）
- 基于代价模型和接受率估计，推导"期望吞吐最大化"的投机长度选择方法；
- 实现：
  - 全局策略（每步根据负载决定统一的投机长度）；
  - 请求级策略（不同请求不同长度，或基于草稿置信度提前终止草稿）；
- 处理 CUDA Graph 兼容性：例如把投机长度离散化到少数几档，每档 capture 一个 graph。

### 4.3 阶段三：评估与分析（必做）
- 在变化的请求率（如 Azure trace 的到达模式）下，对比：不投机 / 各静态配置 / 你的策略；
- 分析策略在什么情况下会做出错误决策，以及错误决策的代价。

### 4.4 进阶（加分）
- 把问题形式化为在线学习 / bandit 问题，与启发式策略对比；
- 结合 MagicDec 的思路：长上下文大 batch 下，用稀疏 KV 草稿降低草稿与验证的 KV 读取开销；
- 草稿树的批感知剪枝：在大 batch 下动态缩小树的宽度。

## 5. 关键知识点（汇报必须讲清楚）

**算法**
- 投机解码期望加速比的推导，以及它在 batch > 1 时为什么不成立；
- 接受率估计方法；你的决策问题的形式化（目标函数、约束）；
- （进阶）bandit / 在线学习的基本概念。

**系统**
- 不同 batch size 下 decode 的 roofline 分析；验证 k 个 token 的代价随 batch 的变化；
- 引擎中投机长度如何影响 KV 分配、调度和 CUDA Graph；
- 为什么每请求不同的投机长度会降低 kernel 效率。

## 6. 实验设计

- **模型**：Llama-3.1-8B-Instruct / Qwen3-8B + 对应 EAGLE-3 草稿器（可用公开权重，如 RedHatAI 或 SpecBundle 发布的草稿模型）；
- **数据**：MT-Bench、HumanEval、GSM8K（不同接受率特征）；在线负载用 ShareGPT + 泊松 / Azure trace 到达；
- **必须产出**：
  1. 加速比 vs 并发度热力图（投机长度 × 并发度）；
  2. 代价模型的拟合效果（预测 vs 实测）；
  3. 自适应策略 vs 静态配置在全负载区间的吞吐曲线；
  4. 动态负载下的时间序列：请求率、所选投机长度、吞吐。

## 7. 答辩追问示例

1. 你的代价模型中，验证代价与哪些因素有关？为什么是这个函数形式？
2. 从 roofline 的角度解释：为什么 batch=64 时投机解码可能变成减速？
3. 你的策略对接受率估计误差的鲁棒性如何？
4. 每请求不同投机长度时，CUDA Graph 怎么处理？带来了多少开销？
5. 换到 H100 和 A100（算力 / 带宽比不同），你的策略需要重新标定吗？

## 8. Agent 使用建议

- 扫描实验、数据分析、拟合脚本可以大量交给 Agent；
- 策略的推导和形式化要由你来完成，并能在白板上讲清楚；
- **风险**：修改引擎中投机长度的逻辑时，容易破坏 KV 回滚和 CUDA Graph 的正确性，一定要保留"输出与不投机一致"的测试。
